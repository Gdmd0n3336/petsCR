# Spec: TASK-03 импорт заведений из OpenStreetMap
**Date:** 2026-10-19
**Author:** Макс (задача из `TASKS.md`), спецификация Claude Code
**Research:** `thoughts/research/2026-10-19-task-03-osm-import.md`
**Size:** M (этапы 1–10)

## Problem
Заведений в базе нет. В OSM по провинции Чонбури уже есть ветклиники, груминги, передержки и зоомагазины. Нужна воспроизводимая выгрузка в промежуточную таблицу, чтобы потом вручную проверить точки (TASK-04), а не писать сырые данные сразу в публичный каталог `venues`.

## Goal
Один ручной запуск скрипта на экспорте из Overpass Turbo (файл вне репозитория) даёт журнал с числами по категориям и файл SQL, который после выполнения (помощник Макса, через свой доступ) заполняет `venues_import` без дублей и без потери уже принятых решений.

## Scope

### In Scope (из `TASKS.md`, «Что сделать»)
1. Скрипт `scripts/import-osm` (TypeScript), запрос Overpass по провинции (`area["ISO3166-2"="TH-20"]`) для тегов `amenity=veterinary`, `shop=pet_grooming`, `amenity=animal_boarding`, `shop=pet`, вывод `out center tags`.
2. Таблица `venues_import`: osm_type, osm_id, tags (jsonb), lat, lng, category (по соответствию тегов), status (`new` | `approved` | `rejected` | `duplicate`), imported_at. Ключ уникальности (osm_type, osm_id).
3. Повторный запуск не создаёт дублей (upsert) и не затирает уже принятые решения по записи.
4. Лог: сколько объектов по каждой категории, у скольких есть телефон и часы работы.
5. Запрос выполняется один раз вручную с небольшой паузой и уважением к лимитам публичного сервера; результат кэшируется в файл вне репозитория.

Добавлено (условия Макса от 2026-10-19):
6. Схема (таблица, индексы, RLS) — только файлом миграции в `supabase/migrations/` с именем по образцу `<YYYYMMDDHHMMSS>_<название>.sql`. Базу применяет Макс; Claude Code базу не трогает.
7. ~~Повтор запроса с паузой~~ — снято решением Макса 2026-10-19: сетевой части нет, только режим `--from-file` на экспорте Overpass Turbo (Макс выгружает его сам с соблюдением лимитов сервера). П. 1 и 5 из `TASKS.md` выполняются так: запрос `out center tags` делает Макс в Overpass Turbo, сохранённый им файл и есть кэш вне репозитория.
8. Доступ к базе — вариант A (решение Макса): скрипт только генерирует SQL-файл, выполняет его помощник Макса через свой доступ.
9. В данных сохраняются `osm_type`, `osm_id` и `source` (решение Макса, для лицензии ODbL).

### Out of Scope
- Перенос из `venues_import` в `venues`, проверка координат, интерфейс проверки (TASK-04).
- Импорт CSV, отзывы (TASK-05).
- Регулярный (по расписанию) импорт, собственный сервер Overpass, любые сетевые запросы из скрипта (решение Макса 2026-10-19).
- Применение миграции и выполнение SQL-файла к рабочей базе (делает Макс).

- [ ] повторный запуск идемпотентен
- [ ] вывод лога показан Максу

Добавлено (уточнения, не ослабляют исходные):
- [ ] (добавлено) Миграция `supabase/migrations/<ts>_venues_import.sql` создаёт `venues_import` с полями из Scope п. 2, `unique (osm_type, osm_id)`, check-ограничениями `category` (те же значения, что у `venues.category`) и `status`; RLS включён; у `anon` и `authenticated` нет прав и политик; права только у `service_role` (как у `venue_line_links`).
- [ ] (добавлено) Повторное выполнение сгенерированного SQL на тех же данных не меняет число строк; изменённые в OSM теги/координаты обновляются; `status`, `category` (решение Макса 2026-10-20: правка человека важнее тегов) и `imported_at` существующих строк не меняются; `osm_timestamp` не затирается пустым значением (тест на SQL-тексте + ручная проверка Макса по инструкции).
- [ ] (добавлено) Значения тегов с `'`, `"`, `\`, `$$`, `;`, `--` и переводами строк не ломают SQL и не исполняются (тест).
- [ ] (добавлено) Объект с несколькими подходящими тегами получает одну категорию по задокументированному приоритету (тест).
- [ ] (добавлено) Скрипт читает только файл (`--from-file`), в сеть не ходит. Если файл не JSON-экспорт Overpass (GeoJSON, XML, битый JSON, нет массива `elements`), скрипт останавливается с понятной ошибкой по-русски и кодом выхода 1 (тест на каждый случай).
- [ ] (добавлено) SQL-файл и журнал пишутся вне репозитория: скрипт отказывается писать внутрь рабочей копии (тест). SQL-файл с данными в репозиторий не коммитится.
- [ ] (добавлено) Каждая строка `venues_import` хранит `osm_type`, `osm_id`, `source = 'osm'` и время данных OSM из файла (`osm3s.timestamp_osm_base`).
- [ ] (добавлено) Миграция проверяется на PGlite (dev-зависимость, точная версия): применение, upsert дважды, сохранение `status`; время CI указано в отчёте.
- [ ] (добавлено) В репозитории, в скрипте и в клиентском коде нет ключей; скрипт не подключается к базе.
- [ ] (добавлено) Журнал содержит: путь к входному файлу, время данных OSM, число элементов по типам (node/way/relation), по каждой категории — всего / с телефоном / с часами работы, число элементов без координат и без нужных тегов (пропущены), дубли в файле, объекты без названия, путь к SQL-файлу.
- [ ] (добавлено) `npm run lint`, `typecheck`, `test`, `build` проходят; `npm audit --audit-level=high` чистый; скрипт не попадает в сборку приложения.

## Constraints
- Приоритет документов: `CLAUDE.md` → `TZ-bulletproof_1.md` → `TASKS.md` → `SKILL.md`.
- Внешние данные недоверенные: теги никогда не исполняются, не склеиваются в SQL.
- Минимальная сложность: без новых зависимостей, если хватает Node 22 (`fetch`).
- Секреты только в переменных окружения и не в репозитории; ключ `service_role` никогда не попадает в клиентский код.
- Подпись «© участники OpenStreetMap» обязательна везде, где данные OSM показываются пользователю (в этой задаче интерфейса нет).
