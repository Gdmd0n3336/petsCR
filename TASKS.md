## TASK-02: схема базы данных (Supabase) — ВЫПОЛНЕНО Claude в чате, остаётся синхронизировать репозиторий
**Статус:** проект Supabase `lapa` создан (ref `fyvsfeiplqqaliqichye`, регион ap-southeast-1), миграция `lapa_initial_schema` применена, проверка безопасности без критичных замечаний, тест RLS пройден (пользователь A не видит заявки B, аноним не видит черновики и заявки, поддельный статус и чужой user_id блокируются).
**Что осталось сделать Claude Code:** (1) подтянуть применённую миграцию в репозиторий (`supabase/migrations/`) через Supabase CLI, способ сверить с актуальной документацией; (2) сгенерировать типы TypeScript и закоммитить; (3) добавить тест политик доступа в репозиторий (на локальной базе или тестовой ветке).
**Отличия от первоначальной спецификации (так и должно остаться):**
- `line_user_id` вынесен из `venues` в отдельную закрытую таблицу `venue_line_links` (иначе он был бы виден через публичный API); читает и пишет только сервер (service_role).
- `venue_metrics` это таблица, а не представление: её заполняет функция `refresh_venue_metrics()`, доступная только серверу (представление над закрытой таблицей заявок не работало бы для публичного чтения).
- `users.id` ссылается на `auth.users(id)`: строка пользователя создаётся сервером после проверки входа через Telegram (TASK-07). Клиент может менять только `users.language`.
- Клиент может создавать заявки только со статусом `sent` и только в опубликованные заведения; менять статусы заявок может только сервер.
**Исходная спецификация ниже оставлена для справки.**

**Контекст:** новый отдельный проект Supabase. Схему проектируем до интерфейса.
**Что сделать:** миграциями создать таблицы и политики доступа.
- `venues`: id, category (`vet_clinic` | `grooming` | `boarding` | `pet_shop`), name_ru, name_th, name_en, district, lat, lng, phone, line_user_id (для привязки аккаунта клиники), website, opening_hours (текст), is_24_7, languages (массив), osm_type, osm_id, coords_verified_at, price_visit_from, price_visit_to, source, source_checked_at, is_demo, is_published, created_at, updated_at.
- `venue_services`: venue_id, service, price_from, price_to, price_source.
- `reviews`: id, venue_id, author_display, rating_overall (1–5), rating_doctors, rating_price, rating_communication (необязательные), text, text_lang, review_date, price_paid, source (`lapa_verified` | `imported` | `demo`), source_url, visit_verified (bool), is_demo, is_published, created_at.
- `users`: id, telegram_id (уникальный), language, created_at.
- `pets`: id, owner_id, species, name, age_years.
- `requests`: id, user_id, venue_id, pet_id, service, requested_time, comment, status (`sent` | `replied` | `booked` | `visited` | `rated` | `declined`), created_at, updated_at.
- `messages`: id, request_id, direction (`client_to_venue` | `venue_to_client`), text_ru, text_th, created_at.
- `venue_metrics`: представление (view), считающее из `requests` среднее время ответа и долю подтверждённых.
**Доступ (RLS):** каталог (`venues`, `venue_services`, `reviews`, `venue_metrics`) читают все, но только записи с `is_published`; запись только серверной ролью. `users`, `pets`, `requests`, `messages` читает и пишет только владелец. Политики покрой тестами.
**Критерии приёмки:** миграции применяются с нуля на чистой базе; проверка безопасности (advisors) без критичных замечаний; тест показывает, что пользователь A не видит заявки пользователя B; сгенерированные типы TypeScript закоммичены.
**Вопросы к Максу до старта:** если что-то в схеме неясно, спроси, не додумывай.

## TASK-03: импорт заведений из OpenStreetMap
**Контекст:** в OSM по Чонбури уже много точек (проверено Максом в Overpass Turbo). Нужна воспроизводимая выгрузка в промежуточную таблицу, а не прямая запись в `venues`.
**Что сделать:**
1. Скрипт `scripts/import-osm` (TypeScript), запрос Overpass по провинции (`area["ISO3166-2"="TH-20"]`) для тегов `amenity=veterinary`, `shop=pet_grooming`, `amenity=animal_boarding`, `shop=pet`, вывод `out center tags`.
2. Таблица `venues_import`: osm_type, osm_id, tags (jsonb), lat, lng, category (по соответствию тегов), status (`new` | `approved` | `rejected` | `duplicate`), imported_at. Ключ уникальности (osm_type, osm_id).
3. Повторный запуск не создаёт дублей (upsert) и не затирает уже принятые решения по записи.
4. Лог: сколько объектов по каждой категории, у скольких есть телефон и часы работы.
5. Запрос выполняется один раз вручную с небольшой паузой и уважением к лимитам публичного сервера; результат кэшируется в файл вне репозитория.
**Критерии приёмки:** тесты на разбор тегов и соответствие категорий на небольшом файле-образце из репозитория; повторный запуск идемпотентен; вывод лога показан Максу.
